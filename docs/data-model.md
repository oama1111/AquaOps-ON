# AquaOps ON — Data Model

Status: draft for Unit 3 design review · Last updated: 2026-09-11
Persistence: SQLAlchemy ORM; SQLite (dev/single-town) with a PostgreSQL
profile for multi-town deployments. All timestamps UTC ISO-8601.

## 1. Entity-relationship overview

```
WATER_SYSTEM 1───* SAMPLING_POINT 1───* CHLORINE_READING
      │                    │                    │
      │                    │                    └──* ANOMALY_ALERT *───1 ALERT_REASON
      │                    │
      │                    └──* REQUIRED_TASK *───1 REG_RULE  (from rules/oreg170.yaml)
      │                              │
      │                    ROUTE_PLAN 1───* ROUTE_STOP *───1 REQUIRED_TASK
      │                              │

      │
      └──* LAB_RESULT_UPLOAD 1───* CHLORINE_READING (provenance)

EVAL_RUN 1───* EVAL_METRIC   (M6 frozen-metric evaluation history)
```

## 3. Integrity & lifecycle rules

- All ingest is idempotent via the uniqueness constraint on
  `chlorine_reading`; replays of the same CSV are safe.
- `required_task` rows are never deleted; status transitions only
  (`pending → planned → done | missed`) — the audit trail is the product.
- Rule changes create new `reg_rule` versions; old tasks keep pointing at
  the version they were generated from.
- Alerts require an explicit acknowledge; acknowledgement feeds the false-
  alarm rate metric in M6.

## 4. Mapping to case data

`sampling_point` is populated from `data/networks/maple_creek_points.csv`
(18 rows). `chlorine_reading` accepts the synthetic 48 h series from
`maple_creek_chlorine_48h.csv` (`source = simulation`) for M2/M6 work
before any real lab data exists.
